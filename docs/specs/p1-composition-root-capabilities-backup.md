# P1：收敛组合根平台效果、能力型 actions 与备份预览边界

## Problem Statement

用户目前可以通过日程页启动计时、管理时间记录，并在设置中预览、导入和导出本地数据，但这些用户可见能力背后的变化知识分散在组合根、`AttentionViewModel` 和备份模块之间。

当计时从不同入口启动时，前台计时服务、恢复提示和通知状态必须保持一致；现在这些平台效果在组合根存在重复路径。用户可能看到计时已经开始，但后续入口的通知提示或恢复处理出现不同步的行为。

页面还间接依赖一个不断增长的 `AttentionViewModel`。新增一个计划、日程、时间记录或备份动作时，调用者需要知道该动作应走普通命令、typed domain command、设置命令还是备份 workflow。这个知识不属于页面，增加了修改一个能力时需要触碰无关能力的范围。

导入预览已经由备份协议产生结构化计数，但组合根仍然重新计算当前状态和候选状态的记录总数。备份记录类型变化时，协议模块、预览文案和组合根必须同步修改，容易出现数量与实际导入结果不一致的情况。

## Solution

保留 `WorkspaceApp` 作为唯一组合根，保留现有页面 `*ScreenState` 与 `*Actions` seam，并在这些 seam 后收敛三个 P1 边界：

1. 新增一个深的 `TimerEffects` 平台 adapter。所有成功的计时启动、暂停和结束都通过同一 adapter 处理前台服务、恢复提示和通知状态；页面只发送 intent。
2. 把 `AttentionViewModel` 的公开动作按变化知识收敛为 `InvestmentActions`、`PlanningActions` 和 `BackupActions` 三个能力接口。一个 ViewModel 可以实现这些接口，但页面和页面 adapter 不再依赖完整 ViewModel。
3. 让 `BackupPreview` 或同等纯 Kotlin preview presentation 拥有记录计数、总数和合并/替换后的摘要计算。组合根只渲染已经准备好的摘要，不再维护备份记录类型清单。

三项改动共用现有的页面 intent seam、反馈宿主、`BackupWorkflow` 和领域命令边界；不改变投入经验、等级、时间记录、备份协议或 Progress Quest 独立会话的产品语义。

## User Stories

1. 作为用户，我想从日程条目启动计时，以便记录与该日程来源关联的实际投入。
2. 作为用户，我想从独立计时入口启动计时，以便记录没有日程来源的实际投入。
3. 作为用户，我想让不同入口启动的计时拥有相同的前台服务、恢复提示和通知行为，以便不必理解入口差异。
4. 作为用户，我想在通知权限未开启时仍能保存计时，以便权限设置不会阻止实际投入记录。
5. 作为用户，我想在计时启动后看到明确的状态反馈，以便知道计时已经开始，而不是只看到页面状态变化。
6. 作为用户，我想暂停、恢复和结束计时，以便处理休息和临时中断；这些操作的系统副作用应与计时状态保持一致。
7. 作为用户，我想让计时结束后停止前台服务并清理恢复提示，以便系统不会继续把已结束的计时当作活动状态。
8. 作为用户，我想让日程页只表达“开始计时”或“结束计时”的意图，以便页面不需要处理 Android 服务和权限 API。
9. 作为用户，我想让计划投入、时间记录和计时器动作保持现有行为，以便重构不会改变实际投入、投入经验和统计。
10. 作为用户，我想让日程条目、目标树和计时器各自只看到所需的动作，以便一个页面的变更不会影响无关页面。
11. 作为用户，我想让计划和日程动作继续使用统一的成功、错误和加载反馈，以便不同入口的操作体验一致。
12. 作为用户，我想让备份预览显示版本、记录分类、总记录数、设置和活动计时器信息，以便在导入前理解数据内容。
13. 作为用户，我想让合并预览和清空后恢复预览使用同一份候选状态，以便预览数字与最终提交一致。
14. 作为用户，我想让备份新增记录类型后预览自动包含该类型，以便不用等待组合根更新另一份计数规则。
15. 作为用户，我想在导入预览中看到合并后或恢复后的预计总数与新增数量，以便判断导入规模和重复数据影响。
16. 作为用户，我想让无效备份在预览阶段被拒绝，以便错误数据不会进入提交或修改本地状态。
17. 作为用户，我想让导入前自动备份、状态指纹检查和恢复最近导入备份继续有效，以便重构不降低数据安全性。
18. 作为用户，我想让 JSON/CSV 导出、导入和恢复仍由原有反馈宿主展示结果，以便页面不会出现第二套错误或成功提示。
19. 作为用户，我想让 Progress Quest 的游戏会话、游戏奖励和游戏前台服务继续独立于 Attention 计时器，以便挂机不会伪造实际投入。
20. 作为用户，我想在应用重建、旋转或进程恢复后看到同一份计时和备份状态，以便平台适配器变化不丢失已提交的数据。

## Implementation Decisions

- `WorkspaceApp` 继续是唯一组合根，负责组装仓库、ViewModel、页面投影、页面 actions adapter 和 Android adapter；页面不接收完整 `AttentionViewModel`。
- `TimerEffects` 是唯一新增的 Android 平台效果 seam。它接收已经成功提交的计时状态变化，并集中处理恢复提示、通知状态反馈、前台计时服务的启动/停止以及进程重建后的同步。计时领域命令仍由 ViewModel/领域层完成，adapter 不创建或修改时间记录。
- 计时入口必须先完成领域状态提交，再调用对应平台效果。领域提交失败时不得启动或重启前台服务；平台提示失败时不得撤销已成功保存的时间记录。已有用户可见的错误与反馈语义保持不变。
- 日程条目启动计时和独立计时使用同一平台效果路径；两者只有时间记录是否带日程来源这一领域参数不同。
- `AttentionViewModel` 对外按变化知识实现三个能力接口：`InvestmentActions` 管理时间记录与计时器，`PlanningActions` 管理目标树、目标阶段、日程、重复日程和迁移，`BackupActions` 管理 JSON/CSV 导出、导入预览、提交和最近导入备份恢复。
- 能力接口不得复制协程生命周期、错误映射、状态订阅或提交锁。它们共享 ViewModel 现有的命令执行和反馈通道；拆分的目标是缩小依赖面，不是复制三个新的门面。
- 页面专属 `*Actions` adapter 只依赖所需的能力接口。组合根可以用同一个 ViewModel 实现多个能力接口，但页面类型签名不能暴露完整 ViewModel、仓储、Room、DataStore、SAF 或 Android 权限 API。
- 现有 `BackupWorkflow` 继续是导入预览、候选状态、状态指纹和提交的编排边界；`AttentionBackupCodec` 继续是 JSON 协议、校验、稳定 ID 合并、里程碑去重和经验规范化的唯一权威。
- `BackupPreview` 或同等纯 Kotlin presentation 类型负责所有记录分类计数、总数计算和候选状态摘要。它可以返回结构化摘要字段或已本地化前的展示事实，但不得依赖 Compose、Android、Room 或文件 URI。
- 组合根的备份预览渲染只消费备份模块返回的摘要；它不得枚举备份记录类型、重新计算当前/候选记录总数或解释协议字段。
- 预览、候选状态和提交必须继续使用同一份 `ImportPlan`。合并和替换模式的用户可见标签可以由组合根渲染，但“预计总数”和“可能新增数量”的计算归备份模块所有。
- 不改变 JSON version 1 的字段外形、稳定 ID 语义、导入覆盖规则、导入前快照、状态指纹闸门或恢复路径。
- 不把 Progress Quest 的游戏会话效果并入 `TimerEffects`。游戏会话仍使用独立的游戏页面、独立前台服务和独立状态；实际投入产生的游戏奖励仍由时间记录结算，不由平台计时器直接发放。
- 迁移按三个可回滚切片完成：先统一计时平台效果，再收敛备份预览归属，最后迁移能力型 actions。每个切片完成后删除旧路径，不保留两套可写入口。

## Testing Decisions

- 测试只断言用户可观察行为、公共调用边界和数据安全不变量，不断言类的私有布局、具体 lambda 数量或组合根的行号。
- 最高级别的计时 seam 是页面 `AgendaActions` 与记录型 fake actions；它验证从日程条目和独立入口发出相同的计时意图，并验证来源参数差异。
- 新增的 `TimerEffects` seam 使用记录型 fake platform effects 验证：成功启动只触发一次恢复提示清理、通知状态处理和前台服务启动；暂停、恢复、结束和重复回调不会产生错误的重复启动或残留服务。真实 Android 服务与权限拒绝路径在宿主/适配层测试覆盖。
- 领域和 ViewModel 测试验证提交顺序：领域命令失败时不触发平台效果；平台效果失败不删除已保存的时间记录；现有错误、成功和加载反馈仍通过同一反馈通道发出。
- 能力型 actions 测试使用现有 `AttentionViewModelTest` 的 fake repository 和 typed command 先例，验证三个能力接口仍产生现有的时间记录、计划、日程、导入和导出结果。测试不得通过完整 ViewModel 类型间接访问页面动作。
- 页面测试使用现有页面 `ScreenState`/`Actions` seam，验证页面只发 intent，不触达 Android、Room、DataStore、SAF 或系统时钟；页面可见文案和可访问反馈保持不变。
- 备份 codec/workflow 测试验证：每种现有记录类型的预览计数、总数与协议内容一致；合并和替换使用同一候选计划；新增记录类型只需在备份模块增加一次计数定义；无效输入在预览阶段失败且不提交。
- 备份预览测试覆盖设置存在/缺失、活动计时器存在/缺失、空备份、重复里程碑、合并无新增、合并有新增和替换候选状态。测试通过结构化摘要断言，不锁定中文行文格式。
- 现有 `BackupWorkflow`、`StateCommitCoordinator`、`AttentionBackupCodec` 和页面反馈测试必须继续通过；新增边界测试应在旧的重复计数或直接平台调用恢复时失败。
- 不新增端到端测试来替代领域和 seam 测试。只有需要验证真实前台服务、通知权限或进程重建时，才增加 Android 宿主级用例。

## Out of Scope

- 不改变计时器、时间记录、规划日、投入经验、等级、达成里程碑或统计的领域规则。
- 不改变 Progress Quest 的角色、游戏经验、游戏会话、奖励账本或独立前台服务设计。
- 不把 `AttentionEngine` 拆成多个规则模块，不重写 `AttentionBackupCodec` 的协议实现，不按文件行数拆分 `AgendaScreen`。
- 不重做页面信息架构、导航层级、视觉语言或反馈文案，只保持现有页面 seam 和用户可见行为。
- 不引入新的持久化表、JSON 字段、备份版本或远程服务。
- 不把三个能力接口变成三个重复的 ViewModel 实现；不要求一次性删除所有历史兼容 API，兼容入口必须转发到唯一的能力/workflow 路径。
- 不在本 spec 内完成 Room 业务快照装配器；该 P2 改动需以独立基线测试和后续 spec 处理。

## Further Notes

- 本 spec 继承组合根与页面 seam、备份 workflow 边界以及 Progress Quest 独立成长边界的既有 ADR；如果实现发现能力接口会迫使页面重新接触 `AttentionState` 或 Android API，应先修订 seam 形状再迁移。
- 本 spec 的关键验收信号是变化放大降低：新增计时入口不复制平台副作用，新增备份记录类型不修改组合根计数，新增页面动作不要求所有页面依赖完整 ViewModel。
- 发布后建议先实现计时平台效果与备份预览归属两个切片，再根据实际调用者数量决定是否继续拆分能力型 actions；若没有第二个独立调用者，能力接口应保持最小而不扩张。
- 领域术语遵循 `CONTEXT.md`：使用“计划”“目标树”“日程条目”“实际投入”“时间记录”“投入经验”和“规划日”，不把这些概念改写成任务、日历日或计划分数。
