## Problem Statement

Attention 的时间记录无法区分它是怎么产生的。现有数据模型只有手动记录、计时和导入三种来源，没有“日程确认”这一种；时间记录与日程条目之间也没有任何关联字段。这带来三个用户可感知的缺陷：

第一，用户在日程上勾选完成时，无法把这次完成和一条实际投入关联起来。时间记录看起来像是凭空出现的一条孤立数据，用户回看时不知道它对应哪次安排。

第二，从某条日程启动计时时，计时器不记得自己属于哪条日程。停止后产生的实际投入同样无法回到它的来源日程，用户需要在多个列表之间人工对照。

第三，按计划确认的记录和精确计时的记录在界面上无法区分。#126 决议明确要求“只有计时路径声称精确的实际开始/结束时间”，而当前模型里两者共用同一个时间戳字段，用户会把按计划确认的记录误读成精确计时结果。

同时，#126 决议确定的视觉语言完全没有落地。仓库里没有主题文件，`Workspace.kt` 是一个 133KB 的单文件，颜色是散落的裸 `Color()` 调用。暖纸色浅色主题、暖炭色深色主题、锈橙/蓝/森林绿/灰/红的品牌语义色都不存在。加载、成功、错误、空数据、权限未开启和本地数据说明这六种状态在各个页面各写各的，Snackbar、内联错误、确认弹窗、禁用态和选中态也没有统一约定。结果是同一个语义在不同页面看起来不一样，用户需要反复学习。

## Solution

让时间记录能说清自己的来源，并把 #126 的视觉语言变成可复用的代码资产。

时间记录增加“日程确认”这一来源，与事后补记、计时产生并列；时间记录和运行中的计时器都增加对日程条目的可空关联。由此，“从日程完成入口提交”“事后补记”“从日程或全局启动计时”三条路径都能产出自解释的记录，按计划确认的记录不再伪装成精确计时结果。日程被移除后记录依然保留，界面给出可解释的说明而不是崩溃或静默丢失。

界面上建立单一的令牌层和组件层。暖纸色与暖炭色两套固定品牌配色提供表面与语义色，不随系统壁纸变化；五种状态用同一组组件表达，每种状态同时由颜色和图标或文字承担，不依赖颜色单独传达信息；时长与计时统一使用自然语言；计划时间与实际时间分开显示，按计划确认的记录标注“按计划记录”。

本轮只做最小接入：现有页面套用这些令牌与组件，不重构信息架构。主导航收敛、工作台重排、目标树改造和所有日期流程属于 #127 至 #130 的后续轮次。

## User Stories

### 记录来源与日程关联

1. As a 用户, I want to 勾选日程完成时创建的实际投入能标明来自这次日程确认, so that 我回看记录时知道它对应哪次安排。
2. As a 用户, I want to 从某条日程启动的计时器记住它属于这条日程, so that 停止后产生的实际投入能回到来源日程。
3. As a 用户, I want to 事后补记的实际投入能选择关联计划但不被强制绑定日程, so that 补记保持轻量。
4. As a 用户, I want to 时间记录列表能反查它属于哪条日程, so that 我不需要在多个列表之间人工对照。
5. As a 用户, I want to 按计划确认的记录被标注为“按计划记录”且不显示精确开始结束时间, so that 我不会把它误读成精确计时结果。
6. As a 用户, I want to 计时产生的记录显示精确的实际时间, so that 精确计时的价值不被稀释。
7. As a 用户, I want to 编辑时间记录时来源、关联日程、规划日和精确时间戳都不变, so that 记录的事实部分保持稳定。
8. As a 用户, I want to 关联的日程被移除后时间记录依然保留, so that 历史投入不会因为日程变动而丢失。
9. As a 用户, I want to 关联的日程不存在时看到“所属日程已删除”这类说明, so that 我理解记录为何没有对应日程。
10. As a 用户, I want to 三种来源都不影响投入经验的计算次数, so that 换一种记录方式不会改变我的成长进度。
11. As a 用户, I want to 导入的旧备份仍然可以打开, so that 升级不会让我丢失历史数据。
12. As a 用户, I want to 导出的时间记录仍然能被既有工具读取, so that 我已有的数据消费方不会因为这次升级而失效。

### 视觉令牌

13. As a 用户, I want to 应用在浅色系统下呈现暖纸色, so that 界面观感统一而不刺眼。
14. As a 用户, I want to 应用在深色系统下呈现暖炭色, so that 深色环境下同样有品牌感。
15. As a 用户, I want to 品牌色不随系统壁纸变化, so that 每次打开都是同一套观感。
16. As a 用户, I want to 正在计时显示为锈橙、已安排显示为蓝色, so that 时间轴上不同状态一眼可分。
17. As a 用户, I want to 已完成显示为森林绿、未归属显示为灰色、错误显示为红色, so that 记录与反馈的状态语义一致。
18. As a 用户, I want to 状态在颜色之外还有图标或文字, so that 我在色觉异常或强光下也能分辨状态。
19. As a 用户, I want to 字号、间距和圆角在所有页面保持同一套层级, so that 界面读起来是一体的。

### 状态与反馈

20. As a 用户, I want to 页面加载中看到统一的加载表达, so that 我知道应用正在工作而不是卡住。
21. As a 用户, I want to 读取失败时看到带重试的错误状态, so that 我能自己恢复而不是卡在错误页。
22. As a 用户, I want to 没有内容时看到空状态和明确的下一步, so that 我知道现在该做什么。
23. As a 用户, I want to 通知权限未开启时看到清楚的说明, so that 我知道它影响什么以及是否必须开启。
24. As a 用户, I want to 看到应用数据只保存在本地的说明, so that 我理解数据的去向。
25. As a 用户, I want to 今天、目标树、所有日期、统计和设置使用同一套状态组件, so that 我只需要学习一次。
26. As a 用户, I want to 操作结果是短时提示而不是打断式弹窗, so that 流程不被打断。
27. As a 用户, I want to 可撤销的删除提供撤销入口, so that 我误删后能找回。
28. As a 用户, I want 表单校验错误显示在出错的位置附近, so that 我知道要改哪里。
29. As a 用户, I want to 危险操作有确认弹窗并说明影响, so that 我不会误删数据。
30. As a 用户, I want to 不可用的操作显示为禁用而不是隐藏, so that 我知道它存在但现在不能用。
31. As a 用户, I want to 选中项同时用颜色和图标或文字表达, so that 我始终知道当前选中了什么。

### 时间表达

32. As a 用户, I want to 时长显示为自然语言, so that 读起来像人话而不是数字加单位。
33. As a 用户, I want to 超过一小时的时长显示为小时与分钟的组合, so that 长时段一眼可读。
34. As a 用户, I want to 不足一小时的时长保持简洁表达, so that 短时段不被冗长的格式撑开。
35. As a 用户, I want to 零时长有明确的表达, so that 它不被显示成空白。
36. As a 用户, I want to 计划时间与实际时间分开显示, so that 承诺和结果不会混为一谈。
37. As a 用户, I want to 时间记录行能看出它来自日程确认、事后补记还是计时, so that 我知道这条数据怎么来的。

### 可访问性

38. As a 使用屏幕阅读器的用户, I want to 状态和操作有语义标签, so that 我能听懂界面在表达什么。
39. As a 使用大字号的用户, I want to 放大字体后布局仍然可用, so that 我能继续使用。
40. As a 用户, I want to 触控目标足够大, so that 我不容易误触。
41. As a 用户, I want to 文字与背景对比度足够, so that 我能看清内容。

## Implementation Decisions

- 领域时间来源枚举在现有手动记录、计时、导入之外增加“日程确认”。手动记录固定表示事后补记；计时是唯一携带精确实际开始与结束时间的来源；日程确认不携带精确时间戳；导入保持备份导入语义。
- 领域时间记录与运行中的计时器各增加一个可空的日程关联字段，并带默认值，以保证既有序列化数据仍可读取。
- 数据层的时间记录表与计时器表各增加一列。数据库版本从 4 升到 5，迁移为纯增量的加列操作，不重写既有行，不引入破坏性回退。
- 既有行的日程关联为空、来源保持原值。不追溯推断历史记录属于哪条日程——历史事实不做无法验证的猜测。
- 时间记录的房间映射、备份导入校验与导出需要随新来源值和新字段保持兼容。备份导入校验增加关联日程的存在性检查。
- 导出维持现有列结构，来源列直接输出新的来源值，不新增列，以免破坏既有导出消费方。
- 领域提供从日程完成入口创建“日程确认”记录的接口，以及让计时器绑定日程的接口；从全局入口启动的计时器不绑定日程。
- 编辑时间记录的既有行为不变：只调整时长、目标归属和备注，保留来源、关联日程、规划日与精确时间戳。
- 读模型对悬挂的日程关联是安全的，展示“所属日程已删除”一类的说明，而不是抛出异常或静默丢弃记录。
- 三种来源不改变投入经验的计算方式：同一笔时间记录只产生一次经验，与来源无关；父目标汇总不重复计算。
- 统计口径不变：实际投入只来自时间记录，新增的来源字段不改变任何聚合结果。
- 新建主题层，提供暖纸色浅色与暖炭色深色两套固定品牌配色，不启用动态取色。
- 品牌语义色为锈橙表示正在计时、蓝色表示已安排、森林绿表示已完成、灰色表示未归属、红色表示错误。
- 主题同时提供间距、圆角与字体三档标度；页面从主题消费颜色，不再写裸色值。
- 主题在应用顶层挂载，覆盖所有现有页面。
- 新建组件层，提供加载中、成功、错误、空数据、权限未开启和本地数据说明六种状态组件，以及 Snackbar 宿主、内联错误、确认弹窗、禁用态和选中态。
- 状态表达不得只依赖颜色，每种状态都必须同时有图标或文字。
- 错误状态提供重试入口，空状态提供明确的下一步，Snackbar 支持可撤销动作。
- 每个共用组件提供稳定标识，供界面测试按语义定位，避免依赖脆弱的文案或层级。
- 新建格式化层，提供自然语言时长表达、“按计划记录”标记、悬挂日程说明，以及计划时间与实际时间分离展示的复用件。
- 日程确认记录只显示“按计划记录”，不展示精确开始与结束时间；计时记录显示精确时间。
- 现有页面只做最小接入：套用主题令牌与共用组件，替换散落的裸色值与重复的内联错误、Snackbar。不改变信息架构与导航结构。
- 本轮不拆分现有的大型界面文件。

## Testing Decisions

好的测试只断言外部可观察行为，不断言实现细节：不检查内部函数被调用了几次、不比对私有字段或组件层级，而是断言用户能看到的时长文案、来源标记、状态语义与主题色值。

采用四层 seam，全部复用仓库既有先例，不新增测试基础设施。

**领域层 seam**使用纯 Kotlin 的状态变换函数作为最高 seam，不触碰房间与界面。既有先例是领域引擎测试。覆盖三种来源各自创建、计时携带精确时间戳、日程确认不携带时间戳、日程计时绑定日程、全局计时不绑定日程、编辑保留来源与关联与规划日与时间戳、悬挂关联读取不抛错、三种来源各只计一次投入经验、父子汇总不重复。

**迁移 seam**使用房间迁移测试助手的运行迁移并校验模式，这是仓库中验证 3 到 4 迁移的既有做法。覆盖版本 4 到 5 迁移后历史行完整、日程关联为空、来源保持原值、统计与投入经验不变。额外覆盖既有旧版本备份仍可导入，以及三种来源与关联在备份导出导入往返后一致。备份编解码与房间映射的既有单测作为补充。

**界面 seam**使用以主界面为宿主的 Compose 界面测试加稳定标识，这是仓库现有界面测试的写法。覆盖五种品牌语义色可按语义取到、浅色与深色两套配色均生效、页面无裸色值残留、同一状态在五个页面使用同一组件与同一标识、每种状态都有可断言的图标或文字、时长自然语言表达覆盖零与不足一小时与超过一小时与跨小时边界、日程确认不显示精确时间而计时显示、计划时间与实际时间可分别断言。

**可访问性 seam**使用 Android 仪器化测试在 API 35 模拟器上断言触控目标尺寸、对比度、动态字体下的布局可用性与语义标签。这一层只在仪器化环境运行，环境限制与代码失败分开记录，不混为一谈。

界面测试沿用既有先例：测试数据通过既有夹具构造，日期与规划日界线固定，避免设备当前时间导致不稳定。

## Out of Scope

- 不重构主导航与信息架构（#127）。
- 不实现“今天”工作台的页面级重排（#128）。
- 不改目标树的浏览与编辑层级（#129）。
- 不实现所有日期的记录流程与实际投入明细查询（#130）。
- 不实现日程条目的删除入口。本轮只保证数据层与读模型对悬挂日程关联安全。
- 不实现实际投入达到计划时长后自动勾选完成的规则（#128）。本轮只保证来源与关联正确。
- 不重建界面原型 HTML 文件。第一轮的可验收证据是 Compose 组件与 API 35 仪器化用例。
- 不拆分现有的大型界面文件。
- 不改变备份文件命名与导出格式的既有结构。
- 不启用动态取色。
- 不改变业务计算规则与统计口径。
- 不新增云同步、账号、多设备协作或服务端能力。

## Further Notes

本规格第一轮的验收证据是代码与仪器化用例，不是原型图。#126 决议中引用的界面原型文件在仓库中并不存在，本轮不重建它；视觉验收通过品牌语义色、深浅两套配色与非仅颜色的状态表达在 Compose 界面测试中完成断言。

后续轮次在本规格实现完成后，回到 #125 地图继续 #131 统计与设置分层、#132 全局反馈与可访问性验收基线。本轮建立的令牌层与组件层是这两个决策票的落地基础，因此组件接口应保持可扩展，但不抢跑 #132 尚未做出的细则。

#130 已决定日程删除只删除日程条目、不删除关联时间记录。当前代码只有添加、更新与切换完成三种日程操作，没有删除入口。本轮通过保证读模型对悬挂关联安全，为后续实现删除入口预先消除数据风险。
